## 开放问题

### Q1. 35M 模型还有提升空间吗

现在的 SFT val 0.0209 没有参考价值。真实的模型能力（69.5%）主要输在：

- 计数（舰种题 0%）
- 摘要（剧情题 20%）
- 意图识别（拒答题 10%）

这三项**是不是根本超出 35M 的能力范围**？如果重训一个 100M 模型（4 GB 显存装不下），
能不能补上？还是必须换方案？

**欢迎讨论：小模型在 RAG 系统里，究竟该负责哪一层。**

### Q2. 评测集怎么才算可信

现在的 200 题是从结构化数据反向生成的，100% 不代表真实水平。

理想做法是收集真实提问 + 人工标注。但：

- 真实提问从哪来
- 开放型问题怎么自动判分
- 标注成本

**欢迎讨论：RAG 系统的最小可信评测集长什么样。**

### Q3. 要不要接外部 LLM

系统现在的定位是「资料检索器」。接一个 API LLM 就能做归纳和建议，
但那就不再是「本地小模型」项目了。

这是**产品定位问题**，不是技术问题：

```
纯本地  → 资料检索器，事实 100% 可信，但不会归纳
接 API  → 真助手，但依赖外部服务、成本、隐私
```

**欢迎讨论：你的场景里，哪个更重要。**

### Q4. 语料重复与版本化

检索 recall@1 被版本化文档低估（V3 / V3.1 / V3.2 同源不同版）。

要不要合并？合并会丢信息（V3.2 可能修了 V3 的错），不合并会拉低指标。

**欢迎讨论：知识库的版本管理策略。**

### Q5. 装配求解器的长尾

359 套通过，77 套归档。其中 13 套是源数据本身错误，其余是：

- T3 子系统技能（槽位由子系统决定）
- 指挥脉冲波链路（需要舰队上下文）
- ≤1.1× 取整

实现这些机制能再收进来十几套，但边际收益在下降。

**欢迎讨论：值不值得做。**

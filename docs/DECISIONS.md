# 决策记录

从语料清洗到模型训练再到交付，**每一个做了选择的地方**。

格式：**决策 → 备选 → 为什么 → 结果 → 事后评价**

评价只有三种：✅ 有效 / ⚠️ 有代价 / ❌ 判断错了

---

## 一、语料阶段

### D01 每篇文档拆成三件套

**决策**：`source.md`（原文不动）/ `meta.yaml`（元数据）/ `rewrite.md`（规范化重写）
**备选**：只存一份重写稿
**为什么**：原文是证据，重写是训练用。混在一起的话，后来发现重写有错就无从对照。
**结果**：654 篇统一结构，后续所有脚本都依赖这个约定。
**评价**：✅ 全项目最省事的决定，没有之一。

### D02 用 SDE 中文名做交叉校验

**决策**：拿 SDE 的 `trnTranslations` 中文表逐条比对语料里的写法
**备选**：信任语料里的写法
**为什么**：语料里同一艘船有四五种写法（多米 / 多米尼克斯 / 多米尼克斯级 / Dominix）
**结果**：发现大量旧译、错译、民间叫法，形成一张对照表。
**评价**：✅ 没有这一步，后面所有结构化都是错的。

### D03 重写而不是直接用原文

**决策**：把原始资料重写成结构清晰的 Markdown
**备选**：直接切块训练
**为什么**：原始资料里混着论坛签名、QQ 群号、广告、乱码。
**结果**：925,585 字，训练数据噪声大幅下降。
**评价**：⚠️ 有效，但代价是**重写者（AI）的理解可能引入偏差**，无法完全校验。

### D04 英文名做主键，中文名只做显示

**决策**：内部一律用 `name_en` 索引，中文名仅在全局唯一时使用
**备选**：中文名做主键（更符合用户直觉）
**为什么**：**「救赎级」同时对应 Absolution 和 Salvation**，中文名做主键会把两条船的数据混在一起（PG 算出 593,337）。
**结果**：修复了装配求解的灾难性错误。
**评价**：✅ 但这是个**代价很高的教训**——一开始就该按主键设计。

### D05 剧情语料只做索引，不做全量结构化

**决策**：379 万字剧情语料 → 71 个词条的索引（出现次数 + 一句原文）
**备选**：全部结构化成事件/势力/时间线
**为什么**：剧情没有稳定的字段结构，强行结构化成本极高。
**结果**：索引可用，但答「萨沙的历史」只能给一句话。
**评价**：⚠️ 当时是合理的妥协，**后来补了 62 个条目文档**才算能看。

### D06 装配单独成主题目录

**决策**：`02_舰船与装配/装配库/` 独立成一个文档，按船名分节
**备选**：混在舰船资料里
**为什么**：装配是高频查询，且格式特殊（逐槽位）。
**结果**：检索「X 怎么配船」能稳定命中。
**评价**：✅

### D07 剔除校验不通过的装配，而不是猜着修

**决策**：435 套里 359 套通过，76 套归档到 `fits_rejected.jsonl` 并写明原因
**备选**：模糊凑数，让通过率好看
**为什么**：一个错的装配比没有装配更糟——用户会照着配，然后配不出来。
**结果**：359 套全部可复现。
**评价**：✅ 但**通过率从 85.4% 降到 84.5%**（因为发现技能减成常数是错的），这个下降是对的。

## 二、结构化阶段

### D08 SDE 是唯一事实来源

**决策**：所有数值一律来自 SDE，语料里的数字不作为事实
**备选**：从语料里抽取数值
**为什么**：语料里的数值会过期、会写错，且无法追溯。
**结果**：7,591 张卡、648,930 个属性值。
**评价**：✅ 这条是后面所有「防胡说」的基础。

### D09 复用 Pyfa 的 eos 引擎，而不是自己写求解器

**决策**：生成 `eve.db`，通过 eos 的 ORM 计算 PG/CPU
**备选**：完全自研
**为什么**：EVE 的属性计算涉及角色加成、技能、植入体、子系统，自己写必然有遗漏。
**结果**：复用成功，但**踩了 `import eos` 拉起 wxPython 的坑**（注入假 config 绕过）。
**评价**：⚠️ 省了大量时间，但引入了一个 LGPL 依赖链，`eve.db` 生成脚本比较脆弱。

### D10 技能减成从 SDE 读，不写死

**决策**：读每个技能的 `powerNeedBonus` / `cpuNeedBonus`
**备选**：统一按 −5%/级
**为什么**：**高级武器升级是 −2%/级**，其它多数是 −5%/级。
**结果**：通过率从虚高的 85.4% 降到真实的 84.5%。
**评价**：✅ 分数变难看了，但那是真相。

### D11 装配校验失败就记录原因，不静默丢弃

**决策**：`fits_rejected.jsonl` 每条带 `_reject_reason`
**为什么**：13 套是**源数据本身错误**（巡洋装备装在驱逐舰上），这些值得反馈给数据源。
**结果**：可追溯。
**评价**：✅

## 三、分词器

### D12 自训 BPE，不用现成中文分词器

**决策**：在语料上训 24,576 词表 BPE
**备选**：用 jieba / bert-base-chinese 的词表
**为什么**：现成词表对 EVE 术语（舰名、装备名）切得很碎。
**结果**：**2.25 字/token**，1024 上下文能装约 2300 汉字。
**评价**：✅ 自训是这类领域模型少数「一定要自己做」的事。

### D13 词表定 24,576

**决策**：24,576
**备选**：32k / 16k
**为什么**：32k 会让 embedding 占比过高（小模型里 embedding 太贵），16k 压缩率不够。
**结果**：embedding 占 24576×384 ≈ 9.4M / 35.4M ≈ 27%。
**评价**：⚠️ 略偏高，但可接受。如果重来可能试 20k。

### D14 预留对话特殊 token

**决策**：`<pad> <bos> <eos> <unk> <|user|> <|assistant|> <|system|> <|context|>`
**为什么**：SFT 阶段需要角色标记，事后再加会改变词表大小、破坏已训权重。
**结果**：SFT 直接用上，无需重训。
**评价**：✅ 一次做对，省掉一整轮返工。

## 四、模型架构

### D15 从零训练，不做微调

**决策**：从随机初始化开始训
**备选**：微调 Qwen/ChatGLM 的小版本
**为什么**：用户明确要求「从零」，且想验证这条路。
**结果**：做到了，但**这正是项目失败的主因之一**（见 WHY-IT-FAILED）。
**评价**：❌ 目标达成了，但目标本身选错了。

### D16 35.4M 参数 / d_model 384 / 16 层

**决策**：深而窄（16 层 × 384）
**备选**：宽而浅（8 层 × 640，即最初的 77M 方案）
**为什么**：4 GB 显存下，深窄结构在相同参数下语言建模更好；640 宽的版本显存不够。
**结果**：batch 2×1024 bf16 占 1.7 GB，能跑。
**评价**：✅ 配置合理，是当时约束下的最优解。

### D17 GQA（8 头 / 4 组 KV）

**决策**：query 8 头，KV 4 组
**为什么**：省 KV cache，长上下文推理更快。
**结果**：生效。
**评价**：✅ 标准做法，没有争议。

### D18 QK-Norm

**决策**：q/k 在 RoPE 之前做 RMSNorm
**为什么**：小模型训练不稳，QK-Norm 能压住 logits 爆炸。
**结果**：训练全程没有出现 loss spike。
**评价**：✅

### D19 RoPE theta 50000

**决策**：50000（而非默认 10000）
**为什么**：想让 1024 上下文的长距离位置编码更平滑。
**评价**：⚠️ 没有做对照实验，属于「按经验选」，**没有证据说它有用**。

### D20 tied embedding

**决策**：输入 embedding 与输出投影共享权重
**为什么**：省 9.4M 参数（占 27%），小模型上收益很大。
**评价**：✅

## 五、训练

### D21 Muon + AdamW 混合优化器

**决策**：2 维矩阵用 Muon（Newton-Schulz 正交化），embedding/norm 用 AdamW
**备选**：全部 AdamW
**为什么**：Muon 在小模型上收敛更稳、对学习率不敏感。
**结果**：112 个矩阵（26.0M）走 Muon，66 个张量（9.5M）走 AdamW。
**评价**：⚠️ 用了，但**没有做 AdamW 对照实验**，无法证明它更好。

### D22 batch 2 × seq 1024 × 累积 4

**决策**：等效 batch 8
**为什么**：显存只够 batch 2；累积 4 补上有效 batch。
**结果**：140 ms/step，14,622 tok/s。
**评价**：✅

### D23 bf16 混合精度

**决策**：autocast bf16
**备选**：fp32（batch 4 时占 3.92 GB，爆）
**评价**：✅

### D24 停在 step 3000，不训满

**决策**：10,200 步的计划，在 3,000 步停下
**为什么**：val 在 3000 步最低（2.87），之后持续上升（4000→2.94，5000→3.35）。
**结果**：留下 `base.pt`。
**评价**：✅ **这是全项目最重要的一个判断**。数据只有 4.25M token，训满等于背下来。

### D25 用 val 而不是 train 判断收敛

**决策**：以验证集 loss 为准
**为什么**：过拟合时 train 会一路下降，train 好看是假象。
**结果**：第 5000 步 train 0.83 / val 3.35，比例 4 倍，一眼看出问题。
**评价**：✅

## 六、SFT

### D26 SFT 数据从结构化资产机械生成

**决策**：不让人写问答，全部由脚本从 SDE / 装配库 / 索引生成
**为什么**：人工写会引入错误，且无法规模化。
**结果**：10,555 条，每条答案都能追溯到数据。
**评价**：✅ 但代价是**问题类型被数据结构限制**（这也是 100% 虚高的来源）。

### D27 只对 assistant 段算 loss

**决策**：user 段标签设 −100
**为什么**：否则模型会学着生成用户问题，学到的是「模仿对话记录」。
**评价**：✅ 标准做法。

### D28 标签必须右移一位

**决策**：`labels[i] = ids[i+1]`
**为什么**：模型的 loss **不做 shift**（预训练时由 `sample_batch` 传 `y=x[1:]`）。
**结果**：第一版没移，loss 掉到 0.002，生成全是「长尾长尾长尾」。
**评价**：❌ 踩过，修好了。**loss 太低要先怀疑标签对齐。**

### D29 context 只放最小证据

**决策**：问低槽就只给低槽，不给整条装配
**备选**：整条装配都塞进去（800+ token，必须截断）
**为什么**：截断会让模型看到残缺资料，学会「猜」。
**结果**：长度从 800 token 降到 80 token，不需要截断。
**评价**：✅

### D30 混入 40% 篡改数值的反向样本

**决策**：context 里的数字随机换成 1~9999，答案必须跟着 context 走
**为什么**：第一版只扰动 ±40%，模型学成「记住真值」而不是「抄 context」。
**结果**：改成全范围随机后，7412 能原样抄对。
**评价**：⚠️ 有效，但**9999→907 这类多位抄写错误仍存在**，最后靠 SDE 兜底解决。

### D31 混入 30% 字段缺失样本（应拒答）

**决策**：拿掉一个真实存在的字段，答案必须是「资料里没有」
**为什么**：不教它说不知道，它会在资料缺失时**挪用邻近字段的数值**（实测把「最大速度 190 m/s」当成护盾容量）。
**结果**：3,341 条。
**评价**：❌ **没成功**。加了 30% 样本，模型仍然不拒答——「判断字段缺失」需要推理能力，35M 做不到。最后靠代码在调模型前拦截。

### D32 学习率 5e-5，只训 3 轮

**决策**：比预训练低一个量级
**为什么**：SFT 阶段用大学习率会把预训练的语言能力冲掉。
**结果**：val 0.0209（无参考价值，数据训了 3 轮）。
**评价**：✅

### D33 序列上限降到 512

**决策**：SFT 用 512 而非 1024
**为什么**：batch 16 × 1024 时 logits 就要 800 MB，直接 OOM。
**评价**：⚠️ 长装配答案会被截。

## 七、护栏与路由

### D34 三道护栏

**决策**：字段缺失检测（调模型前）/ 数值闭集校验（生成后）/ SDE 确定性兜底
**为什么**：模型会编数字（实测答 235，真值 3200）。
**结果**：事实类从 94% 提到 100%。
**评价**：✅ **这是全项目最有效的工程决策**。

### D35 未知字段一律拒答

**决策**：句式匹配「X 的 Y 是多少」，Y 不认识就拒答
**为什么**：白名单匹配会漏掉没见过的词（「矿石产出速率」），模型就编一个。
**评价**：✅ 宁可少答。

### D36 价格类问题拒答

**决策**：识别「多少钱/价格/造价」，直接说没有
**为什么**：资料里没有市场数据，硬答就是编。
**结果**：修掉了「多米尼克斯装满多少钱 → 中能量槽是 5 个」。
**评价**：✅

### D37 属性路径必须真的问到字段

**决策**：句子里有船名不够，必须有字段词才走属性路径
**为什么**：否则「装满要多少钱」会被劫持成属性题。
**结果**：修掉实体劫持。
**评价**：✅ 路由条件要精确到意图，不能只看提到了什么。

### D38 舰种/词条走确定性查表

**决策**：直接读索引文档，不经过模型
**为什么**：裸模型答「无畏舰有几艘」是 0%，答「X 是什么」是 20%。
**结果**：两类都到 100%。
**评价**：✅

### D39 查表用最长匹配

**决策**：按名称长度降序匹配
**为什么**：「枪骑兵级无畏舰」里同时含「无畏舰」，按字典序会先命中「无畏舰」（答 13 艘，实际 4 艘）。
**评价**：✅

### D40 对比题只列数据，不下判断

**决策**：「A 和 B 哪个好」→ 并列两者属性 + 明说「资料里没有直接的取舍结论」
**为什么**：资料里确实没有观点，编一个就是假建议。
**评价**：✅ 诚实，但**用户体验不算好**——用户想要的是结论。

### D41 缩写表内置 16 条

**决策**：T3C/AB/MWD/ECM/DCU/EHP 等，直接给定义
**为什么**：这类问题是明确的事实查询，查表 100% 确定。
**结果**：T3C 从「舰队集结通知」变成「T3C = 战略巡洋舰」。
**评价**：⚠️ 覆盖有限，词典类问题应该更系统地做。

### D42 越界问题用词表拦截

**决策**：正则匹配「版本/现实/诗/建造」等
**为什么**：拦截比让模型判断便宜且可靠。
**评价**：⚠️ 词表必然有漏（漏了「建造」一次，补上了）。**这是打补丁，不是解决方案。**

### D43 非结构化问题给「来源 + 最贴题一句」

**决策**：不再整段丢原文，改为结构化摘录
**为什么**：整段丢出去用户不知道该看哪句。
**结果**：配船问题能直接看到「毒蜥级适合伽玛深渊」。
**评价**：⚠️ 比之前好，但**仍然不是「回答」**。

## 八、检索

### D44 bge-small-zh 走 ONNX，不装 torch 版

**决策**：onnxruntime + 90.5 MB 模型
**为什么**：省显存、省依赖、启动快。
**结果**：单次查询 21 ms。
**评价**：✅

### D45 混合检索 α=0.55

**决策**：向量 0.55 + BM25 0.45
**为什么**：EVE 术语（舰名、装备名）靠词面匹配更准，纯向量容易糊。
**结果**：recall@10 97.7%。
**评价**：⚠️ α 是手调的，**没有系统搜索**。

### D46 不引入 LangChain / LlamaIndex

**决策**：全部自研约 2000 行
**为什么**：需求明确（检索 + 路由 + 护栏），框架会带来大量用不上的抽象。
**评价**：✅ 代码可控，问题可定位。

### D47 reranker 否决

**决策**：实测后不加
**数据**：recall@1 81.7% → 78.0%，MRR 0.882 → 0.859，每题 +500 ms。
**为什么失败**：评测查询取自原文段落，词面重合度本来就高。
**评价**：❌ 尝试失败，但**负结果本身有价值**，已写进文档。

### D48 索引块大小固定切分

**决策**：按字符数切块，未做语义切分
**为什么**：先跑通，没时间做语义分块。
**评价**：⚠️ **这是检索质量的上限所在**。语义分块可能还能提升，但没做。

## 九、评测

### D49 端到端 200 题，六类，机械判分

**决策**：事实/装配/舰种/词条/拒答/字段缺失
**为什么**：每类都能机械判断对错，不需要人工。
**评价**：❌ **最大的失误**——题目按系统已有能力生成，导致 100% 虚高。

### D50 装配判分用并集

**决策**：一艘船多套配置，命中任一都算对
**为什么**：第一版要求命中特定一套，把正确行为判成错误（65% → 100%）。
**评价**：✅ 但**暴露了评测设计缺乏前瞻**。

### D51 数值判分按单位取数

**决策**：优先取贴着单位的数字
**为什么**：「威帕斯改良型350mm磁轨炮的 PG 是 1559」里第一个数字是 350。
**评价**：✅

### D52 数值校验用数值比较而非字符串

**决策**：`1.0` 与 `1` 视为相等
**评价**：✅

### D53 单列裸模型分数

**决策**：`--no-guard` 跑一次
**结果**：69.5%
**评价**：✅ **这个数字比 100% 更有价值**，它揭示了系统能力的真实来源。

### D54 补测真实口语提问

**决策**：用 7 个真实问题测
**结果**：全错，暴露评测集问题。
**评价**：✅ 但**太晚了**，应该在项目中期就做。

### D55 检索单独评测

**决策**：300 题 recall@k / MRR
**结果**：recall@1 81.7% / @10 97.7%
**评价**：✅ 量完才知道检索不是瓶颈，省下无谓优化。

## 十、交付

### D56 CLI → HTTP → 前端

**决策**：先命令行，再 FastAPI + 单页 HTML
**为什么**：先保证能力，再包装。
**评价**：✅

### D57 多轮用状态机，不用模型

**决策**：会话保存实体，指代改写由代码做
**为什么**：模型记不住上文（评测里多轮能力为 0）。
**结果**：「那它的中槽呢」→「毒蜥级的中槽装什么」。
**评价**：✅

### D58 README 直接声明是失败品

**决策**：第一段就说失败，附 100% vs 69.5% 的对照
**为什么**：一个「看起来成功」的仓库会误导别人照抄。
**评价**：✅ 诚实比好看重要。

### D59 仓库不含权重和索引

**决策**：`.gitignore` 排除 `ckpt/` `index/` `models/` `refs/` `data/sde/`
**为什么**：总 1.3 GB，且都能用脚本重建。
**结果**：仓库 38.5 MB。
**评价**：✅

### D60 按开发阶段提交

**决策**：11 次提交，每条对应一个阶段
**为什么**：让 git log 本身就是时间线。
**评价**：✅

### D61 MIT + 第三方条款

**决策**：代码 MIT，但单列 SDE / Pyfa / 语料 / 模型的各自条款
**为什么**：代码许可不能覆盖数据许可。
**评价**：✅

### D62 中英双语 README

**决策**：`README.md` + `README.en.md`
**评价**：⚠️ 只有 README 和复盘文档双语，其余文档中文——**英文读者会断层**。

# 时间线：这个项目是怎么一步步做出来的

按实际开发顺序记录，包含每一步的判断依据和踩到的坑。
比 README 更详细，目的是让别人知道**为什么是这样做的**，而不只是做成了什么样。

硬件全程：RTX 3050 Laptop，4 GB 显存。

---

## 阶段 0：语料（第 1–3 天）

**起点**：手上有一批 EVE 中文资料（攻略、小说、词典、装配帖），格式混乱，重名严重。

| 步骤 | 做了什么 | 结果 |
|---|---|---|
| 0.1 | 按主题建目录规范，每篇文档拆成 `source.md` / `meta.yaml` / `rewrite.md` | 654 篇 |
| 0.2 | 交叉校验：SDE 中文名 vs 语料里的写法 | 发现大量错译、旧译、民间叫法 |
| 0.3 | 重写规范化 | 925,585 字 |
| 0.4 | 建索引：舰种索引（48 组）、世界观词条索引（71 条） | 供检索用 |

**关键判断**：不直接拿原始文本训练。原因——语料里同一艘船有多种写法（「多米」/「多米尼克斯」/「多米尼克斯级」），
不统一的话模型会学到互相矛盾的映射。

**踩的坑**：

- 中文舰名不唯一。**「救赎级」同时对应 Absolution 和 Salvation**，按中文名建索引会把两条船的数据混在一起（PG 算成 593,337）。
  → 改成**一律用英文名做主键**，中文名只在全局唯一时才用。
- SDE 的 `groups.jsonl` 里 `name` 是本地化字典，不是字符串，直接索引会得到 `{'zh':…}`。

## 阶段 1：结构化资产（第 4–6 天）

语料是给人读的，模型需要的是可计算的结构。

| 资产 | 数量 | 来源 |
|---|---|---|
| SDE 卡片 | 7,591 张 | `types.jsonl` + `dogmaAttributes` + 中文翻译表 |
| 装配库 | 359 套（159 艘船） | 从装配帖解析，用 eos 求解器逐条校验 |
| 舰船属性表 | 426 艘 | SDE |

**装配求解器**：直接复用了 Pyfa 的 eos 引擎（LGPL-2.1，通过生成 `eve.db` 间接调用，仓库里不含其源码）。
自己重写了一遍 PG/CPU 计算，但技能减成一开始是错的——

**踩的坑**：

- **所有技能都按 −5%/级 计算**。实际上只有大部分技能是 −5%，**高级武器升级是 −2%/级**（V 级 −10%）。
  修正后通过率从「虚高的 85.4%」降到真实的 84.5%。
  → 教训：**宁可数字难看，也要真实。**
- `isDefault: False` 过滤掉了一批角色加成效果，导致大量装配算不过。
- 中文船名冲突（同上）导致求解器把战列舰的装备拿到驱逐舰上算。

最终：435 套装配里 **359 套通过**，77 套归档并标注原因（13 套是源数据本身错误，其余是 T3 子系统技能、指挥脉冲波链路、1.1× 取整）。

## 阶段 2：模型（第 7–12 天）

### 2.1 分词器

自训 BPE，24,576 词表。训练语料上压缩率 **2.25 字/token**。

中文模型常见的坑是直接用英文分词器，一个汉字被切成 2–3 个 token，上下文浪费一半。
自训之后 1024 上下文能装约 2300 个汉字。

### 2.2 架构

```
d_model 384 / 16 层 / 8 头（GQA，KV 4 组）/ d_ff 1024 SwiGLU
RoPE theta 50000 / QK-Norm / tied embedding / max_seq 1024
参数 35.4M
```

**为什么是这个尺寸**：4 GB 显存下，batch 2 × 1024 seq + bf16 + 梯度累积 4 是稳定上限（1.7 GB）。
再大的模型在 4.25M token 的数据量下也只会更快过拟合。

**优化器**：Muon（2 维矩阵）+ AdamW（embedding / norm）。Muon 用 Newton-Schulz 做正交化，
在小模型上收敛比纯 AdamW 稳。

### 2.3 预训练

```
4,252,169 token（train 4,167,126 / val 85,043）
batch 2 × 1024 × accum 4，lr 6e-4，warmup 200
```

**踩的坑（最重要的一个）**：

- 一路训到 **step 5000，val 从 2.87 涨到 3.35**，train 掉到 0.83。
  模型开始**流利地背诵训练语料**，但答非所问。

  实测对比（同一个提示词）：

  | 权重 | 输出 |
  |---|---|
  | step3000（val 2.87） | `1. 堡垒/低安/低安/低安/低安…`（复读） |
  | step5000（val 3.35） | `纤维和纤维（俗称黑洞），包括无洞…2. 什么是势力战争？`（通顺但跑题） |

  → 停在 **step 3000**。数据只有 4.25M token，20 轮就等于背下来。

## 阶段 3：SFT（第 13–15 天）

### 3.1 数据

10,555 条，来源全部可追溯：

| 类型 | 条数 |
|---|---|
| 舰船属性 | 1,278 |
| 装备属性 | 3,980 |
| 装配 | 1,835 |
| 多轮追问 | 396 |
| 字段缺失（应拒答） | 3,341 |
| 舰种 / 词条 / 越界拒答 | 51 |

**关键设计**：context 只放回答所需的最小证据。第一版把整条装配塞进 context（800+ token），
必须截断，而截断会让模型看到残缺资料、学会「猜」。

**踩的坑**：

- **标签没做位移**。模型的 loss 不做 shift（预训练时由 `sample_batch` 传 `y=x[1:]`），
  直接传同位置标签会学成「复述当前 token」——loss 掉到 0.002，生成全是「长尾长尾长尾」。
  → 修正为 `labels[i] = ids[i+1]`。
- 序列超长（1200 > 1024）直接崩，因为 context + 装配正文太长。
- 显存 OOM：batch 16 × 1024，光 logits 就要 800 MB → 降到 batch 4 × 512。

最终 val 0.0209。**这个数字没有意义**（数据训练了 3 轮），真正的检验是端到端评测。

## 阶段 4：护栏（第 16–18 天）

裸模型实测：问「毒蜥级护盾容量」，答 **235**（真值 3200）。它编了一个数。

于是确立分工：**模型只负责措辞，事实由代码保证**。

三道护栏：

| 护栏 | 时机 | 作用 |
|---|---|---|
| 字段缺失检测 | 调模型之前 | 问题字段不在 context → 直接拒答 |
| 数值闭集校验 | 生成之后 | 答案里每个数字必须出现在 context |
| SDE 确定性兜底 | 生成之后 | 模型数字写错 → 换成模板答案 |

**踩的坑**：

- **字段表不全**：SDE 里本来就有信号半径、跃迁速度、锁定距离，我只收了 12 个字段，
  问这些时被误判「字段缺失」。
- **未知字段放行**：问「矿石产出速率」时护栏不认识这个字段，放行，模型就编一个。
  → 改成句式匹配：只要问的是「X 的 Y 是多少」而 Y 不认识，一律拒答。
- **实体劫持**：「多米尼克斯级装满要多少钱」里有船名，被当成属性题，答成「中能量槽是 5 个」。
  → 属性路径必须真的问到了字段才启用。

## 阶段 5：评测（第 19–21 天）

### 5.1 端到端 200 题

| 类别 | 题数 | 初始 | 最终 |
|---|---:|---:|---:|
| 事实 | 100 | 81% | **100%** |
| 装配 | 40 | 65% | **100%** |
| 舰种 | 20 | 5% | **100%** |
| 剧情 | 20 | 5% | **100%** |
| 拒答 | 10 | 50% | **100%** |
| 字段缺失 | 10 | 50% | **100%** |
| **总计** | **200** | **59.5%** | **100%** |

七轮修复，两次「改坏了」被评测拦住：

- 单字段 context：94% → 93%（模型失去定位信息）
- 被问字段后置：94% → 78%（和 SFT 训练分布不符）

**没有评测，这两个改动会被当成优化留下来。**

### 5.2 裸模型对照

```
带护栏  100.0%
裸模型   69.5%
```

差 30.5 个百分点，全部来自确定性代码。裸模型真正会的只有两件事：抄写结构化字段（94%）、
复述装配槽位（100%）——恰好是 SFT 覆盖的两种模式。

### 5.3 检索评测

端到端分数掩盖了检索质量，所以单独测：

| 指标 | 数值 |
|---|---:|
| recall@1 | 81.7% |
| recall@3 | 95.0% |
| recall@5 | 96.7% |
| recall@10 | 97.7% |
| MRR | 0.882 |

**结论：检索不是瓶颈**，正确答案几乎总在前 10 条。

## 阶段 6：真实提问暴露问题（第 22 天）

用 7 个真实口语问题测，**7 个全错**：

| 问 | 答 |
|---|---|
| 配一条刷四级深渊的船，推荐什么 | 深渊建筑介绍片段 |
| 毒蜥和伊什塔哪个好 | 只给伊什塔属性卡 |
| 新手怎么赚钱快 | 商人攻略碎片 |
| 多米尼克斯装满多少钱 | **中能量槽是 5 个** |
| T3C 是什么船 | 舰队集结通知 |

**根因**：200 题是按系统已有能力设计的，真实问法一条都没覆盖。

修复：

- 对比题 → 并列两者属性，明说「资料里没有直接的取舍结论」
- 价格题 → 拒答（资料里没有市场数据）
- 缩写 → 16 条查表（T3C/AB/MWD/ECM…），用 ASCII 边界匹配（中文在正则里算 word 字符，`\b` 失效）
- 开放问题 → 结构化摘录：来源 + 最贴题的一句，标明「未作归纳」

## 阶段 7：验证 reranker（第 23 天，负结果）

检索 recall@1 只有 81.7%，想用交叉编码器重排提升。

下载 bge-reranker-base（int8，266 MB），对 top-30 重排：

| | recall@1 | recall@10 | MRR | 耗时 |
|---|---:|---:|---:|---:|
| 基线 | **81.7%** | 97.7% | **0.882** | 21 ms |
| 加重排 | 78.0% | 97.3% | 0.859 | +500 ms |

**更慢且更差，否决。** 代码保留在 `rag/rerank.py`，默认关闭。

原因：评测查询取自原文段落，词面重合度本来就高，交叉编码器带不来新信息。

## 阶段 8：服务化（第 23 天）

- 多轮状态机：指代改写（「那它的中槽呢」→「毒蜥级的中槽装什么」）
- FastAPI + 单页前端：`/chat`、`/search`、`/health`

**踩的坑**：追问判定过松，「无畏舰有几艘」被改写成「巴盖斯级无畏舰有几艘」。
→ 收紧为「必须有指代前缀，或只有字段且短于 12 字」。
